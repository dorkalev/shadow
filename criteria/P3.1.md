# P3.1 — Collection Limited to Stated Purposes

## Criterion (AICPA TSP Section 100, verbatim)
> Personal information is collected consistent with the entity's objectives related to privacy.

## What it means
The Privacy category is optional — it applies only if the company includes Privacy in its SOC 2 scope (most tiny startups don't; they cover privacy via GDPR/CCPA programs instead).

Short criterion, simple idea: only collect the personal information your privacy notice says you collect, for the purposes it states, by fair and lawful means. If your policy says you collect name, email, and usage data, but your signup form also grabs phone numbers and your backend logs full request bodies containing user content, you have a collection gap — either stop collecting or update the notice first.

For AI-first startups the sharp edge is incidental collection: prompts, uploaded files, and chat transcripts routinely contain personal information about the user and third parties. Telemetry, LLM request logging, and error trackers (Sentry breadcrumbs, full-prompt logging for debugging) are all "collection." The control is knowing what flows in, keeping a data inventory that matches reality, and minimizing what you capture (scrub PII from logs, don't log prompt bodies by default).

## Points of focus (2022 revision, summarized)
These are summaries of the AICPA points of focus, not verbatim:
- Personal information is limited to that which is necessary for the purposes identified in the privacy notice.
- Personal information is collected by fair and lawful means, without deception.
- Information is collected from reliable sources; third-party sources are assessed for reliability and lawful handling.
- Data subjects are informed when additional information beyond what was originally requested is needed.

## What the auditor will ask for
- The data inventory / record of processing activities (what PI is collected, where, why, from whom).
- The privacy notice, to compare stated collection against actual collection.
- A walkthrough of collection points: signup form, product inputs, SDKs/trackers on the site, server logs.
- List of third-party data sources (enrichment APIs, imported contact lists) and diligence on them.
- Evidence of data minimization decisions (e.g., PII scrubbing in logging config, fields removed from forms).
- Any new collection introduced during the period and the corresponding notice update.

## How a tiny AI-first startup satisfies it
- Maintain `compliance/data-inventory.md` in git: a table per data category (identity, billing, prompts/content, telemetry) with source, purpose, storage location, retention, and vendor exposure. Update it in the same PR that adds a new field or tracker.
- Keep forms minimal — collect email + name at signup, nothing speculative. Every new PI field requires a PR that also touches the data inventory (enforceable convention).
- Log hygiene: disable full prompt/response logging in production by default; configure Sentry/pino/structured logging with PII redaction; document exceptions.
- Site trackers: one analytics tool, listed in the privacy notice and cookie banner; no ad pixels unless disclosed.
- If enriching from third-party sources (e.g., Clearbit), record the vendor and lawful basis in the inventory and DPA list.

## Automated shadow checks
| Check | Source | Method |
|---|---|---|
| Data inventory file exists, parses, and was updated in the last 12 months | GitHub | File existence; `git log -1 -- compliance/data-inventory.md` date |
| Signup/API request schemas collect only fields listed in the inventory | GitHub | Grep user model, signup form, and public API schemas; diff field names against inventory table |
| No undisclosed trackers on the marketing site/app | Public website | Fetch pages, extract third-party script domains, compare against inventory/subprocessor list |
| Production logging config redacts PII / does not log prompt bodies | GitHub | Grep logging config for redaction settings; flag `console.log(prompt)`-style patterns and Sentry `sendDefaultPii` |
| New PI-bearing DB columns appear in inventory (migration diff) | GitHub | Parse migrations merged in period for name/email/phone/address-like columns; check inventory mentions them |
| Privacy notice collection section is a superset of inventory categories | Public website + GitHub | Fetch policy, keyword-match inventory categories |
| Fairness/lawfulness of third-party sources | — | MANUAL — reviewer assesses any enrichment vendors |

## Evidence artifacts
- `compliance/data-inventory.md` — the record of processing, with git history showing updates.
- Merged PRs that added collection points alongside inventory updates.
- Logging/redaction configuration files (e.g., Sentry init, logger config) at commit SHAs in the period.
- Tracker scan output from the shadow tool (`evidence/site-trackers-<date>.json`).
- Screenshot of signup form fields vs. inventory extract.
- Vendor/DPA entries for any third-party data sources.
