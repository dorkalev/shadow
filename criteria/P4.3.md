# P4.3 — Secure Disposal of Personal Information

## Criterion (AICPA TSP Section 100, verbatim)
> The entity securely disposes of personal information to meet the entity's objectives related to privacy.

## What it means
The Privacy category is optional — it applies only if the company includes Privacy in its SOC 2 scope (most tiny startups don't; they cover privacy via GDPR/CCPA programs instead).

When personal information is no longer needed — retention expired, account deleted, deletion request received — it must be destroyed so it can't be recovered or misused. "Securely" means actual deletion (or irreversible anonymization/redaction), across all the places the data lives: primary DB, object storage, search indexes, caches, logs, analytics, vendor systems, and eventually backups. Soft-delete flags that leave data queryable forever do not count as disposal.

For a cloud-only startup there's no shredding hard drives — secure disposal means: deletion requests are captured and tracked, a deletion routine covers every store in the data inventory (this is why the inventory matters — you can't delete from stores you forgot exist), vendor deletion is invoked (LLM providers, analytics, email tools), and backup expiry is understood and documented. A user-facing account-deletion endpoint plus an internal runbook covers most of it.

## Points of focus (2022 revision, summarized)
These are summaries of the AICPA points of focus, not verbatim:
- Requests for deletion of personal information are captured, identified, and flagged for action.
- Personal information is disposed of, destroyed, or redacted in a manner that prevents recovery, in accordance with the retention schedule and commitments.
- Disposal covers all locations where the information is stored, including copies held by third parties/processors.
- Disposal actions are documented, and completion is verified.

## What the auditor will ask for
- The disposal/deletion procedure or runbook (what gets deleted from where, in what order).
- Evidence of deletion request intake and tracking (tickets/queue for account-deletion and DSAR-deletion requests).
- A completed deletion sample: request → execution → verification (queries showing the subject's data gone).
- Code for the deletion endpoint/job, showing coverage of all relevant stores.
- Vendor deletion evidence: how processor-held copies are removed (API calls, support confirmations, DPA deletion clauses).
- Explanation of backup handling: how deleted data ages out and what happens on restore.

## How a tiny AI-first startup satisfies it
- Build one `deleteUser(userId)` code path (API endpoint + admin CLI) that cascades through every store in `compliance/data-inventory.md`: DB rows (hard delete or crypto-erase), object storage prefixes, search index docs, cache keys, analytics user deletion API, email tool contact deletion.
- Deletion requests: self-serve "Delete account" in settings, plus privacy@ email that becomes a Linear ticket (label `dsar-deletion`) with a due date (30 days).
- Runbook `compliance/runbooks/deletion.md`: steps, vendor deletion endpoints (e.g., analytics user-deletion API, email provider contact delete), and a verification query per store.
- Backups: document that backups expire in ≤35 days and that any restore is followed by re-running pending deletions; note this in the runbook.
- Log the deletion: an audit record (subject hash, timestamp, stores cleared) retained as proof without retaining the PI.

## Automated shadow checks
| Check | Source | Method |
|---|---|---|
| Deletion endpoint/routine exists in code | GitHub | `gh search code` for delete-account route / `deleteUser` job across repos |
| Deletion routine touches every store listed in the data inventory | GitHub | Static cross-check: store names in `data-inventory.md` vs. identifiers referenced in the deletion module |
| Deletion runbook exists and updated within 12 months | GitHub | File existence + last-commit date on `compliance/runbooks/deletion.md` |
| DSAR-deletion tickets closed within SLA (e.g., 30 days) | Linear API | Query issues labeled `dsar-deletion`; compare created vs. completed dates |
| Deletion audit log entries exist for completed deletion tickets | Production DB / logs | Query deletion-audit table count vs. closed ticket count |
| Vendor deletion API calls present in deletion path | GitHub | Grep deletion module for analytics/email-provider deletion API calls |
| Soft-delete-only anti-pattern absent (hard delete or crypto-erase used) | GitHub | Grep for `deleted_at`-only handling in the deletion path; flag if no hard delete/purge stage |
| Verified end-to-end deletion of a sample subject | Production systems | MANUAL — run verification queries from the runbook, attach output |

## Evidence artifacts
- Deletion endpoint/job source code and its test file, at commit SHAs in the period.
- `compliance/runbooks/deletion.md` — per-store steps and verification queries.
- Closed `dsar-deletion` Linear tickets with verification output attached.
- Deletion audit log export (subject hash, timestamp, stores) for the period.
- Vendor deletion confirmations (API responses or support emails) in `compliance/evidence/`.
- Backup retention config export supporting the age-out claim.
