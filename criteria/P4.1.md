# P4.1 — Use Limited to Identified Purposes

## Criterion (AICPA TSP Section 100, verbatim)
> The entity limits the use of personal information to the purposes identified in the entity's objectives related to privacy.

## What it means
The Privacy category is optional — it applies only if the company includes Privacy in its SOC 2 scope (most tiny startups don't; they cover privacy via GDPR/CCPA programs instead).

Purpose limitation: personal information collected for purpose A may only be used for purpose A (and compatible purposes disclosed in your notice). The classic failures for an AI startup: using customer prompts/content to train or fine-tune models when the notice only mentions "providing the service"; letting engineers query production user data for ad-hoc analysis; copying production PII into staging or local dev environments; or repurposing signup emails for a cold-outreach campaign for a different product.

The control is a documented purpose per data category (that's the data inventory again) plus guardrails that keep use inside those purposes: access controls on production data, no-PII-in-lower-environments practice, vendor settings that disable training on your API data (OpenAI/Anthropic API defaults), and a review step before any new use of existing data.

## Points of focus (2022 revision, summarized)
These are summaries of the AICPA points of focus, not verbatim:
- Uses of personal information are limited to the purposes identified in the entity's privacy notice and objectives.
- Personal information is used for new purposes only after obtaining consent or providing notice, as required.
- Access to and use of personal information by personnel is restricted to those with a business need.
- Contractual or policy commitments limiting use (including by vendors/processors) are established and monitored.

## What the auditor will ask for
- Data inventory showing the documented purpose for each PI category.
- Privacy notice sections describing uses, to compare against actual product behavior.
- Access control evidence: who can access production PI (IAM roles, DB access list) and why.
- Vendor configuration evidence that processors don't use your data beyond providing the service (LLM provider training settings, DPAs).
- Any new-use decisions during the period and the associated notice/consent update (or attestation of none).
- Policy for using production data in development/testing (anonymization/synthetic data practice).

## How a tiny AI-first startup satisfies it
- Purposes live in `compliance/data-inventory.md`; any new use of an existing data category requires a PR updating the inventory and, if user-visible, the privacy notice — same rule as new collection.
- LLM providers: use API tiers with training disabled by default (OpenAI API, Anthropic API); capture the DPA and a screenshot/setting export proving zero-retention or no-training options where enabled.
- Production access: only founders/on-call engineers hold DB or GCP/AWS console access to PI; everyone authenticates via Google Workspace SSO; no shared credentials.
- Dev/test data: seed scripts and synthetic fixtures instead of prod dumps; if a prod copy is ever needed, scrub PII first and note it in a Linear ticket.
- Marketing: only email users who opted in (P2.1 flags), and only about the product they signed up for.

## Automated shadow checks
| Check | Source | Method |
|---|---|---|
| Every PI category in inventory has a stated purpose | GitHub | Parse `compliance/data-inventory.md` table; flag empty purpose cells |
| Production data access restricted to a small named set | GCP/AWS | `gcloud projects get-iam-policy` / `aws iam` list; diff members against approved list in `compliance/access-matrix.md` |
| No prod-DB connection strings or dumps referenced in dev tooling/seeds | GitHub | Grep repos for prod DSN patterns in seed/test/fixture paths |
| LLM API usage points at no-training endpoints/orgs; no consumer-key usage | GitHub | Grep for API base URLs/org IDs; verify env var names match the approved org |
| Fixtures/seeds contain no real-looking PII | GitHub | Regex scan fixtures for real email domains (non-example.com), phone patterns |
| Marketing sends limited to opted-in users | Email provider API | Query provider audience/segment definitions for the opt-in filter |
| Vendor no-training/DPA settings verified | Vendor dashboards | MANUAL — export/screenshot from OpenAI/Anthropic org settings |

## Evidence artifacts
- `compliance/data-inventory.md` purpose column, with git history.
- IAM policy exports (GCP/AWS) and DB user list for the period.
- `compliance/access-matrix.md` — who may access production PI and why.
- LLM vendor DPA PDFs and org-settings screenshots (training disabled / retention settings) in `compliance/evidence/`.
- Seed/fixture files demonstrating synthetic data; Linear ticket for any sanctioned prod-data copy.
- Email provider segment definition export showing opt-in filtering.
