# A1.1 — Capacity monitoring and management

## Criterion (AICPA TSP Section 100, verbatim)
> The entity maintains, monitors, and evaluates current processing capacity and use of system components (infrastructure, data, and software) to manage capacity demand and to enable the implementation of additional capacity to help meet its objectives.

## What it means
This category is optional — it applies only if the company includes Availability in its SOC 2 scope.

The criterion asks a simple question: do you know how much headroom your system has, and would you notice before you ran out? "Capacity" covers compute (CPU/memory on your services), storage (database disk, object storage), and quotas (API rate limits, connection pools, LLM provider token limits). The auditor wants evidence that you measure current usage, compare it against limits, and have a way to add capacity before customers feel it.

For a 1–10 person startup on GCP or AWS, most of this is inherited from managed services: Cloud Run / ECS autoscale, Cloud SQL storage auto-grows, and the provider handles physical capacity. What is *not* inherited is knowing your own limits — instance size caps, max connections, provider quotas, and third-party rate limits (e.g., Anthropic/OpenAI tokens-per-minute). The control you actually own is monitoring plus alerting thresholds plus the ability to scale up (usually a one-line config change reviewed via PR).

## Points of focus (2022 revision, summarized)
These are guidance to consider, not requirements:
- **Measures current usage** — usage of system components is measured against committed capacity and tolerances (summary).
- **Forecasts capacity** — expected demand is projected and compared to available capacity, including growth (summary).
- **Makes changes based on forecasts** — capacity is expanded or resources reallocated when forecasted demand approaches limits (summary).

## What the auditor will ask for
- Screenshots or exports of capacity/utilization dashboards (CPU, memory, disk, request rates) covering the audit period.
- Configured alerting policies with thresholds for resource utilization, and an example alert that fired with the follow-up.
- Autoscaling configuration for production services (min/max instances, scaling triggers).
- Database storage settings showing auto-resize or documented headroom review.
- Evidence of capacity planning — a recurring review note, Linear ticket, or scaling PR from the period.
- Description of how third-party quota limits (cloud quotas, LLM API rate limits) are tracked.

## How a tiny AI-first startup satisfies it
- **Use managed autoscaling everywhere**: Cloud Run/GKE Autopilot/ECS Fargate with min/max instance counts set in Terraform or service YAML. The scaling config in the repo *is* the control.
- **Enable storage auto-grow**: Cloud SQL `storageAutoResize: true` (or RDS storage autoscaling). Zero-effort, fully evidenced by `gcloud` output.
- **Cloud Monitoring alert policies** on CPU > 80%, memory > 80%, disk > 80%, and error-rate spikes, routed to Slack/PagerDuty. A handful of policies is enough at this scale.
- **Track LLM/provider quotas**: a short note in the runbook listing rate limits per provider and the dashboard that shows consumption; alert on 429s.
- **Lightweight capacity review**: a quarterly Linear ticket ("capacity review Q3") where someone glances at dashboards and records "fine" or files scaling work. Ten minutes, real evidence.
- **Inheritance**: physical/host capacity is the cloud provider's responsibility — reference their SOC 2 report as a subservice organization (CSOC) and rely on it in the system description.

## Automated shadow checks

> Datastore commands are per-stack: Cloud SQL shown. On Firestore stacks (the blessed `provision/gcp`), the equivalents are `gcloud firestore databases describe` (PITR, delete protection, state) and `gcloud firestore backups list` / `backups schedules list` (schedule present, recent snapshots).
| Check | Source | Method |
|---|---|---|
| Autoscaling configured on prod services | GCP | `gcloud run services describe <svc> --format=json` → verify `autoscaling.knative.dev/maxScale` annotation set and > minScale |
| DB storage auto-resize enabled | GCP | `gcloud sql instances describe <inst> --format="value(settings.storageAutoResize)"` → expect `True` |
| DB disk utilization headroom | GCP | `gcloud sql instances describe <inst>` → compare `settings.dataDiskSizeGb` vs current usage metric via `gcloud monitoring` API |
| Utilization alert policies exist | GCP | `gcloud alpha monitoring policies list --format=json` → ≥1 policy on CPU/memory/disk metrics with notification channel |
| Notification channel wired | GCP | `gcloud alpha monitoring channels list --format=json` → verified channel (Slack/email/PagerDuty) exists and enabled |
| Quarterly capacity review performed | GitHub | `gh api repos/<org>/<repo>/contents/compliance/capacity-reviews/` → file dated within last 100 days |
| LLM provider quota tracking documented | — | MANUAL — review runbook section listing provider rate limits and monitoring approach |
| Capacity forecast reasonableness | — | MANUAL — auditor judgment on whether thresholds/growth assumptions make sense |

## Evidence artifacts
- `compliance/capacity-reviews/YYYY-QN.md` in the main repo — quarterly review notes (date, dashboards checked, findings, tickets filed).
- Terraform/service config in repo showing autoscaling min/max — permalink to file at a commit within the period.
- `gcloud sql instances describe` JSON export (storage auto-resize, disk size) — saved to evidence folder at collection time.
- `gcloud alpha monitoring policies list` JSON export — alert policies and thresholds.
- Screenshot of Cloud Monitoring dashboard covering the audit window.
- One example alert notification (Slack message or PagerDuty incident) with resolution, if any fired.
