# P7.1 — Accurate and Complete Personal Information

## Criterion (AICPA TSP Section 100, verbatim)
> The entity collects and maintains accurate, up-to-date, complete, and relevant personal information to meet the entity's objectives related to privacy.

## What it means
The Privacy category is optional — it applies only if the company includes Privacy in its SOC 2 scope (most tiny startups don't; they cover privacy via GDPR/CCPA programs instead).

If Privacy is in scope, this criterion is about data quality: the personal information you hold should be accurate (correct values), up-to-date (reflecting changes), complete (not missing pieces that would mislead), and relevant (you don't hoard fields you have no purpose for — this overlaps with data minimization). Bad PI quality causes real privacy harm: notices sent to the wrong address, decisions made on stale data.

For a small SaaS this is mostly product mechanics: validate PI at input (email verification, format checks), let users view and edit their own profile data (self-service correction is the strongest control), propagate corrections to downstream systems and vendors, and periodically prune irrelevant or stale fields. The auditor wants to see the controls, not perfect data.

## Points of focus (2022 revision, summarized)
Summarized from the AICPA 2022 points of focus:
- PI is validated for accuracy and completeness at collection (edit checks, verification).
- Data subjects can review and update or correct their PI.
- Corrections are propagated to relevant systems and, where applicable, to third parties holding the data.
- PI is periodically reviewed for currency, completeness, and relevance to the stated purposes.
- Data collected is limited to what is relevant to the entity's purposes.

## What the auditor will ask for
- Description/demonstration of input validation on PI collection points (signup, profile forms).
- Evidence of email verification or equivalent identity/accuracy checks.
- Demonstration of user self-service profile edit (screenshots or a test account walkthrough).
- The correction procedure, including how corrections reach downstream vendors, and any correction requests handled in the period.
- Data inventory/schema showing PI fields mapped to purpose (relevance justification).
- Evidence of a periodic data-quality/relevance review (ticket, script output, or pruning migration).

## How a tiny AI-first startup satisfies it
- Enforce validation in code: schema-level constraints (NOT NULL, format checks), email verification on signup, typed forms. Point the auditor at the validation layer (e.g., Pydantic/zod schemas) in the repo.
- Ship a profile/settings page where users edit their own name/email/etc. — self-service correction closes most of this criterion.
- Correction propagation: when a user updates their email, sync to your email vendor/CRM via webhook or nightly job; document the flow in one paragraph.
- Keep a data inventory (`compliance/data-inventory.md`): table of PI fields → purpose → source → retention. Fields with no purpose get dropped in a migration — commit is the evidence.
- Annual "data relevance review" as a recurring Linear ticket: walk the inventory, prune stale fields, run a null/garbage-rate query on key PI columns and record results.

## Automated shadow checks

| Check | Source | Method |
|---|---|---|
| Data inventory file exists mapping PI fields to purposes | repo `compliance/data-inventory.md` | Existence + table parse |
| Validation schemas cover PI models (email format, required fields) | repo code | `gh search code` / grep for zod/Pydantic validators on user models |
| Email verification flow present in codebase | repo code | Grep for verification-token/confirm-email routes |
| Profile update endpoint/page exists | repo code | Grep routes for profile/settings update handlers |
| Annual data-quality review ticket completed | Linear API | Query recurring ticket status |
| Data-quality metrics query (null/invalid rate on PI columns) | production DB | MANUAL — or scripted read-only query if DB access granted |
| Users can actually edit their PI in the UI | product | MANUAL — screenshot walkthrough |

## Evidence artifacts
- `compliance/data-inventory.md` — PI field → purpose → retention table.
- Validation schema files (paths noted, e.g., `src/models/user.py` / `schemas/user.ts`).
- Screenshots of profile edit and email verification flows in `compliance/evidence/`.
- Migration commits removing irrelevant PI fields.
- Annual data-quality review ticket with query output attached.
