# C1.2 — Disposal of confidential information

## Criterion (AICPA TSP Section 100, verbatim)
> The entity disposes of confidential information to meet the entity's objectives related to confidentiality.

## What it means
This category is optional — it applies only if the company includes Confidentiality in its SOC 2 scope.

C1.1 covers keeping confidential data; C1.2 covers getting rid of it when you no longer should have it. Two triggers matter: a retention period expiring (per your own retention schedule) and a customer request — churned customers asking for deletion is the case that actually happens to startups. The auditor wants a defined disposal procedure and evidence it was followed, not a shredding certificate: for cloud-native companies "disposal" means deleting rows/objects, expiring backups that contain them, and confirming copies (analytics, logs, LLM provider retention) are covered.

The trap for tiny startups is copies: you delete the customer's rows in Postgres but the data lives on in PITR backups for 7 days, in GCS exports forever, in a BigQuery analytics dataset, and in log retention. The honest control is a deletion runbook that enumerates every location from the C1.1 data inventory, states how each is handled (immediate delete vs. aging out with backup rotation — aging out is acceptable if documented), and a ticket per deletion request recording completion. GCS lifecycle rules and log retention settings automate the boring part.

## Points of focus (2022 revision, summarized)
These are guidance to consider, not requirements:
- **Identifies confidential information requiring disposal** — procedures exist to identify confidential information that has reached the end of its retention period or is otherwise designated for destruction (summary).
- **Destroys confidential information** — identified information is erased or otherwise destroyed, including copies, in a manner that prevents recovery (summary).
- Commonly assessed alongside: disposal commitments to customers (e.g., DPA deletion clauses, deletion-on-termination SLAs) are defined and met, and disposal actions are recorded (summary).

## What the auditor will ask for
- Data retention and disposal policy/schedule (retention period per data type, disposal method per storage location).
- Deletion runbook or procedure covering all systems from the data inventory, including backups and third-party processors.
- Log of disposal events during the period: customer deletion requests and scheduled retention-based purges, with completion evidence.
- A sampled deletion request walked end-to-end: request → ticket → deletion executed → confirmation to customer.
- Automated lifecycle/retention configurations (GCS lifecycle rules, log retention settings, backup retention).
- Contract language (DPA) defining deletion obligations and timelines, and evidence timelines were met.

## How a tiny AI-first startup satisfies it
- **Retention schedule inside the classification policy**: one table — data type → retention → disposal method. Example: customer content: life of contract + 30 days; logs: 30–90 days; backups: 7–35 day rotation.
- **Automate what the platform can do**:
  - GCS lifecycle rules (`gcloud storage buckets describe` shows them) to auto-delete/age objects.
  - Cloud Logging retention set explicitly per bucket (`gcloud logging buckets describe`).
  - Cloud SQL backup retention bounds how long deleted data survives in backups — document that backups age out rather than being surgically edited (standard, auditor-accepted).
- **Deletion runbook** (`docs/runbooks/customer-data-deletion.md`): per-system steps (DB delete script, GCS prefix removal, analytics dataset, LLM provider — note zero-retention API terms mean nothing to delete there), plus confirmation step.
- **Ticket per disposal event**: a Linear ticket labeled `data-deletion` per customer request or scheduled purge, closed with command output/screenshot attached. The label makes it queryable evidence.
- **Offboarding hook**: customer churn checklist includes "run deletion runbook, file ticket" so requests aren't dropped.
- If zero disposal events occurred in the period, that's fine — the auditor tests design (policy + runbook + automated lifecycle configs) instead of operation.

## Automated shadow checks

> Datastore commands are per-stack: Cloud SQL shown. On Firestore stacks (the blessed `provision/gcp`), the equivalents are `gcloud firestore databases describe` (PITR, delete protection, state) and `gcloud firestore backups list` / `backups schedules list` (schedule present, recent snapshots).
| Check | Source | Method |
|---|---|---|
| Retention/disposal policy exists, reviewed < 12 months | GitHub | `gh api repos/<org>/<repo>/contents/docs/policies/data-classification.md` → contains retention table; commit date via `gh api .../commits?path=...` |
| Deletion runbook exists and covers inventory systems | GitHub | `gh api .../contents/docs/runbooks/customer-data-deletion.md` → exists; cross-check section headers against `compliance/data-inventory.yaml` entries |
| GCS lifecycle rules configured | GCP | `gcloud storage buckets describe gs://<bucket> --format="json(lifecycle)"` → rules match policy retention for that bucket's data class |
| Log retention set per policy | GCP | `gcloud logging buckets describe _Default --location=global --format="value(retentionDays)"` → matches policy (e.g., ≤ 90) |
| Backup retention bounded | GCP | `gcloud sql instances describe <inst>` → `retainedBackups` and `transactionLogRetentionDays` within policy limits |
| Deletion tickets closed with evidence | Linear | Linear API: issues with label `data-deletion` in period → all closed, each has attachment/comment with execution output |
| Deletion request SLA met | Linear | Linear API: `data-deletion` issue completed-at minus created-at ≤ DPA timeline (e.g., 30 days) |
| Deletion actually removed data | — | MANUAL — auditor samples a deleted customer and confirms absence in DB/buckets |
| Copies in third parties disposed | — | MANUAL — verify LLM provider retention terms and any manual purge confirmations |

## Evidence artifacts
- Retention table in `docs/policies/data-classification.md` (retention + disposal method per data type).
- `docs/runbooks/customer-data-deletion.md` — per-system deletion procedure including backup aging rationale.
- Linear export of `data-deletion` labeled tickets for the period, each with execution output attached.
- `gcloud storage buckets describe` JSON exports showing lifecycle rules; `gcloud logging buckets describe` output showing retention days.
- One end-to-end sample package: customer request email → ticket → deletion script output → confirmation sent.
- DPA excerpt defining deletion obligations (redacted customer copy in Drive evidence folder).
