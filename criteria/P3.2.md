# P3.2 — Explicit Consent Before Collection

## Criterion (AICPA TSP Section 100, verbatim)
> For information requiring explicit consent, the entity communicates the need for such consent as well as the consequences of a failure to provide consent for the request for personal information and obtains the consent prior to the collection of the information to meet the entity's objectives related to privacy.

## What it means
The Privacy category is optional — it applies only if the company includes Privacy in its SOC 2 scope (most tiny startups don't; they cover privacy via GDPR/CCPA programs instead).

Where P2.1 covers consent generally, P3.2 is specifically about the moment of collection for information that requires explicit consent — typically sensitive personal information (health, biometrics, precise location, financial account data) or anything your notice or applicable law says needs an affirmative opt-in. Three things must happen, in order: tell the person why you need consent, tell them what happens if they decline (e.g., "the feature won't work"), and get the consent before you collect the data — not after.

Most tiny SaaS startups can largely design this criterion away: don't collect sensitive categories. If your product does (e.g., a health-adjacent AI assistant, voice recording, calendar/email access via OAuth), the consent screen is the control: it must appear before the data flows, state the purpose and consequences, and the grant must be recorded. OAuth consent screens (Google Workspace scopes) count as part of this story and should request minimal scopes.

## Points of focus (2022 revision, summarized)
These are summaries of the AICPA points of focus, not verbatim:
- The entity identifies the types of personal information that require explicit consent (including sensitive information) before collection.
- The need for consent and the consequences of declining are communicated to the data subject at or before the point of collection.
- Explicit consent is obtained prior to collecting the information, and the consent is documented and retained.
- Consent obtained covers only the stated purpose; collection does not proceed without it.

## What the auditor will ask for
- The entity's definition/list of data types requiring explicit consent (usually in the privacy policy or consent basis doc).
- Screenshots or walkthrough of the consent prompt shown before collection (feature opt-in modal, OAuth scope screen, upload disclaimer).
- Text of the consequence disclosure ("if you decline, X won't be available").
- Sample consent records showing consent timestamp precedes first collection of that data type.
- Code or config evidence that collection is gated on the consent flag (feature-flag check, scope check).
- Any denied-consent handling: what the system does when a user declines.

## How a tiny AI-first startup satisfies it
- In `compliance/consent-basis.md`, add an "explicit consent required" column; mark sensitive categories. If none are collected, state that explicitly — that's a valid and common answer.
- For any sensitive feature (mic/voice, calendar/email OAuth, file upload of sensitive docs): show a purpose + consequences modal before enabling; persist `feature_consent_at` per user; gate the collection code path on that flag.
- Request minimal OAuth scopes; incremental authorization (ask for calendar scope only when the calendar feature is enabled).
- Declining is non-punitive: the rest of the product works; the modal says exactly what is lost.
- Keep consent copy in the repo (component text), so changes are PR-reviewed and versioned.

## Evidence artifacts
- `compliance/consent-basis.md` with the explicit-consent column (or "no sensitive data collected" statement).
- Screenshots/recordings of the pre-collection consent modal and OAuth consent screen in `compliance/evidence/`.
- Consent component source files and their git history (copy changes reviewed via PR).
- Redacted sample of consent records showing consent timestamp < first-collection timestamp.
- OAuth client scope configuration export.
- Test file (if present) asserting the collection path is blocked without consent.
