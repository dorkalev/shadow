# A1.2 — Environmental protections, backups, recovery infrastructure

## Criterion (AICPA TSP Section 100, verbatim)
> The entity authorizes, designs, develops or acquires, implements, operates, approves, maintains, and monitors environmental protections, software, data backup processes, and recovery infrastructure to meet its objectives.

## What it means
This category is optional — it applies only if the company includes Availability in its SOC 2 scope. **However, this file carries weight 2**: even when Availability is out of scope, auditors routinely map data backup and recovery controls to the common criteria (typically CC7.5 / CC9.1 as part of incident recovery and risk mitigation), so backups are effectively always in scope. Treat the backup portion of this criterion as mandatory regardless of scoping decisions.

The criterion bundles three things: (1) environmental protections — power, cooling, fire suppression, physical resilience of the data center; (2) data backup processes — what gets backed up, how often, where, and whether it's protected; and (3) recovery infrastructure — the ability to stand the system back up (multi-zone deployment, restorable snapshots, infrastructure-as-code).

For a tiny cloud-native startup, environmental protections are entirely inherited from GCP/AWS as a subservice organization — you do not run generators or HVAC, and your system description should say so explicitly. What you own is the backup configuration (automated backups + point-in-time recovery on Cloud SQL, versioning on GCS buckets), backup monitoring (would you know if backups silently failed?), and recovery infrastructure (Terraform that can rebuild the environment, multi-zone or documented single-zone risk acceptance).

## Points of focus (2022 revision, summarized)
These are guidance to consider, not requirements:
- **Identifies environmental threats** and designs detection/protection measures against fire, flood, power loss, temperature (summary — inherited from cloud provider for cloud-native entities).
- **Implements and maintains environmental protection mechanisms** and responds to environmental threat events (summary — inherited).
- **Determines data requiring backup** — data is classified and backup scope defined based on criticality (summary).
- **Performs data backup** — backups run per schedule, are monitored for success/failure, and failures are remediated (summary).
- **Addresses offsite/replicated storage** — backup copies are stored in a separate location or region (summary).
- **Implements alternate processing infrastructure** — recovery infrastructure exists to resume processing if primary fails (summary).

## What the auditor will ask for
- Backup configuration for all production data stores (Cloud SQL settings showing automated backups, PITR, retention).
- Evidence backups actually ran throughout the period (backup run list/logs, sampled across months).
- Evidence of backup failure alerting and any failure follow-ups.
- Backup/DR policy or runbook section: what's backed up, frequency, retention, restore procedure, RTO/RPO targets.
- Multi-zone/region configuration for production, or a documented risk acceptance for single-zone.
- The cloud provider's SOC 2 report (subservice organization) and your annual review of it, covering environmental protections.
- Infrastructure-as-code repo demonstrating the environment can be rebuilt.

## How a tiny AI-first startup satisfies it
- **Cloud SQL automated backups + PITR**: `enabled: true`, `pointInTimeRecoveryEnabled: true`, `transactionLogRetentionDays: 7`, retained backups ≥ 7. This one config satisfies most of the criterion and is fully verifiable by CLI.
- **GCS versioning or soft delete** on buckets holding customer data; lifecycle rules documented.
- **Backup failure alerting**: a Cloud Monitoring alert (or scheduled shadow check) on backup job failures — silent backup failure is the classic audit finding.
- **Everything in Terraform**: the recovery infrastructure story for a tiny startup is "we can re-apply Terraform to a new project/region." Keep state remote and the repo current.
- **Short DR runbook** (`docs/runbooks/disaster-recovery.md`): what's backed up, retention, restore steps, RTO/RPO (e.g., RTO 4h / RPO 1h), single-region rationale if applicable.
- **Inheritance**: environmental protections (power, fire, cooling, physical redundancy) are GCP/AWS responsibility. List them as a subservice organization, use the inclusive-of-CSOCs mapping in the system description, and review their SOC 2 report annually (record the review as a ticket or dated note).
- **HA where cheap**: Cloud SQL regional (HA) tier or documented decision not to; multi-zone Cloud Run is automatic.

## Automated shadow checks

> Datastore commands are per-stack: Cloud SQL shown. On Firestore stacks (the blessed `provision/gcp`), the equivalents are `gcloud firestore databases describe` (PITR, delete protection, state) and `gcloud firestore backups list` / `backups schedules list` (schedule present, recent snapshots).
| Check | Source | Method |
|---|---|---|
| Automated backups enabled | GCP | `gcloud sql instances describe <inst> --format="value(settings.backupConfiguration.enabled)"` → `True` |
| Point-in-time recovery enabled | GCP | `gcloud sql instances describe <inst> --format="value(settings.backupConfiguration.pointInTimeRecoveryEnabled)"` → `True` |
| Backup retention ≥ 7 | GCP | `gcloud sql instances describe <inst> --format="value(settings.backupConfiguration.backupRetentionSettings.retainedBackups)"` |
| Recent backups succeeded | GCP | `gcloud sql backups list --instance=<inst> --limit=14 --format=json` → all `status: SUCCESSFUL`, most recent < 26h old |
| DB high availability | GCP | `gcloud sql instances describe <inst> --format="value(settings.availabilityType)"` → `REGIONAL` (or flag + require documented acceptance) |
| Bucket versioning/soft delete | GCP | `gcloud storage buckets describe gs://<bucket> --format=json` → `versioning.enabled` or `softDeletePolicy` present |
| DR runbook exists and is current | GitHub | `gh api repos/<org>/<repo>/contents/docs/runbooks/disaster-recovery.md` → exists; last commit touching it < 12 months (`gh api .../commits?path=...`) |
| Terraform covers prod resources | GitHub | `gh api repos/<org>/<infra-repo>/contents/` → Terraform files exist; drift check MANUAL |
| Provider SOC 2 reviewed annually | GitHub | `gh api repos/<org>/<repo>/contents/compliance/vendor-reviews/` → GCP/AWS review file dated within 12 months |
| Environmental protections adequate | — | MANUAL — inherited; auditor reviews cloud provider SOC 2 report and CUEC mapping |

## Evidence artifacts
- `gcloud sql instances describe` JSON export — backup config, PITR, retention, availability type (timestamped, saved per evidence run).
- `gcloud sql backups list` JSON export — proof of successful backup executions sampled across the audit period.
- `docs/runbooks/disaster-recovery.md` — backup scope, retention, restore procedure, RTO/RPO.
- `compliance/vendor-reviews/gcp-YYYY.md` — annual review of provider SOC 2 report noting environmental protection coverage.
- Terraform repo permalink demonstrating infrastructure-as-code recovery capability.
- Alert policy export + example backup-failure alert (if any occurred) with remediation ticket.
