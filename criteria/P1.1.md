# P1.1 — Privacy Notice to Data Subjects

## Criterion (AICPA TSP Section 100, verbatim)
> The entity provides notice to data subjects about its privacy practices to meet the entity's objectives related to privacy. The notice is updated and communicated to data subjects in a timely manner for changes to the entity's privacy practices, including changes in the use of personal information, to meet the entity's objectives related to privacy.

## What it means
The Privacy category is optional — it applies only if the company includes Privacy in its SOC 2 scope (most tiny startups don't; they cover privacy via GDPR/CCPA programs instead).

If Privacy is in scope, this criterion asks the most basic question: do the people whose personal data you process actually know what you do with it? "Notice" in practice means a published privacy policy that describes what personal information you collect, why, how long you keep it, who you share it with, and what rights data subjects have. The notice has to be accurate — a policy that says "we never share data" while you pipe user data into third-party LLM APIs is worse than no policy.

The second sentence is where audits usually find gaps: the notice must be kept current and changes must be communicated in a timely way. If you start sending user content to a new AI subprocessor, or begin using data for model training, the privacy policy must be updated before or at the time the practice changes, and users must be told (email, in-app banner, changelog on the policy page).

## Points of focus (2022 revision, summarized)
These are summaries of the AICPA points of focus, not verbatim:
- Notice is communicated to data subjects, describing the personal information collected and the purposes of collection, use, retention, disclosure, and disposal.
- Notice is provided in a timely manner — at or before the point of collection, and when practices change.
- Notice covers the entities, products, and activities it applies to, so data subjects know its scope.
- Notice is written in clear, conspicuous, plain language and is readily accessible where data is collected.

## What the auditor will ask for
- URL of the published privacy policy and evidence it is linked from the product and signup flow.
- Version history / change log of the privacy policy covering the audit period, with dates.
- Evidence of communication of at least one policy change during the period (email blast, in-app notice, release note) — or attestation that no changes occurred.
- The internal process/procedure for reviewing and updating the notice (who owns it, review cadence).
- Mapping showing the notice accurately reflects current practices (e.g., all AI/LLM subprocessors listed or covered).
- Screenshot of policy link at points of collection (signup page, footer, cookie banner).

## How a tiny AI-first startup satisfies it
- Host the privacy policy as a page generated from a markdown file in the website repo (`site/privacy.md`). Git history is your change log; add a visible "Last updated" date and a human-readable changelog section at the bottom.
- Link it in the site footer, signup screen, and cookie banner. One PR per policy change, reviewed by the founder who owns privacy.
- Keep a `compliance/subprocessors.md` list (OpenAI/Anthropic, GCP/AWS, analytics) and reference it from the policy; update both in the same PR when a vendor is added.
- Announce material changes via a product email or in-app banner; save a copy of the sent email in `compliance/evidence/`.
- Annual review reminder as a recurring Linear ticket ("Review privacy policy"), closed with a link to the review PR or a "no changes needed" note.

## Automated shadow checks
| Check | Source | Method |
|---|---|---|
| Privacy policy URL returns 200 and contains required sections (collection, use, retention, disclosure, rights, contact) | Public website | `curl` policy URL, grep for section keywords |
| Policy content unchanged vs. stored canonical copy; if changed, flag for review of communication evidence | Public website + local store | Fetch, normalize HTML, diff against `evidence/privacy-policy-snapshot.html` |
| "Last updated" date on policy is within 12 months or matches latest repo change | Public website / GitHub | Parse date from page; `gh api` last commit date on `site/privacy.md` |
| Policy source file exists and has ≥1 reviewed PR touching it in the period (or explicit no-change attestation) | GitHub | `gh pr list --search "privacy" --state merged`; `git log -- site/privacy.md` |
| Subprocessor list file exists and every LLM/cloud vendor in code (SDK imports) appears in it | GitHub | Grep repos for `openai`/`anthropic`/`@google-cloud` imports; diff against `compliance/subprocessors.md` |
| Annual policy-review ticket exists and was completed | Linear API | Query issues labeled `privacy-review` completed in period |
| Change-communication evidence (email/banner) exists for each policy change | — | MANUAL — reviewer confirms artifact in `compliance/evidence/` |

## Evidence artifacts
- `site/privacy.md` (or equivalent) with git history — the policy and its change log.
- `compliance/evidence/privacy-policy-snapshot-<date>.html` — periodic captures by the shadow tool.
- `compliance/subprocessors.md` — current subprocessor/vendor list referenced by the policy.
- Merged PRs updating the policy, with reviewer approval visible.
- Copy of change-notification email or screenshot of in-app banner in `compliance/evidence/`.
- Closed Linear ticket for the annual privacy policy review.
