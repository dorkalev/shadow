# A1.3 — Recovery plan testing

## Criterion (AICPA TSP Section 100, verbatim)
> The entity tests recovery plan procedures supporting system recovery to meet its objectives.

## What it means
This category is optional — it applies only if the company includes Availability in its SOC 2 scope.

A1.2 says you must *have* backups and recovery infrastructure; A1.3 says you must *prove they work*. An untested backup is a hope, not a control. The auditor wants evidence that at least once during the audit period you actually exercised the recovery procedure — restored a database backup, rebuilt infrastructure from Terraform, or walked through the DR runbook — and recorded the result, including whether restored data was complete and how long it took.

For a tiny startup this does not mean a full failover drill with a war room. The accepted minimum is an annual (semi-annual is better) restore test: clone the production Cloud SQL instance from a backup or PITR timestamp into a scratch instance, run a few row-count/integrity queries, note elapsed time against your RTO/RPO targets, write it up, delete the scratch instance. Two hours of work, and it is one of the highest-signal artifacts in the whole audit — it also frequently gets mapped into CC7.5 even when Availability is out of scope.

## Points of focus (2022 revision, summarized)
These are guidance to consider, not requirements:
- **Implements business continuity plan testing** — recovery/continuity procedures are tested periodically, at a frequency matching the environment's rate of change (summary).
- **Tests speed of recovery** — testing measures whether recovery time meets defined objectives (RTO), and identified gaps drive plan updates (summary).
- **Tests integrity and completeness of backup data** — restored data is verified as complete and accurate, confirming backups are usable (summary).

## What the auditor will ask for
- The recovery/DR plan document that was tested.
- Restore test report(s) from the audit period: date, who performed it, procedure followed, elapsed time vs. RTO, data verification performed, issues found.
- Evidence the test actually happened (Cloud SQL operation logs showing a restore/clone, terminal output, screenshots).
- Follow-up tickets for any gaps identified during testing and their resolution.
- Test schedule or policy statement defining testing frequency (e.g., annually).
- If applicable, evidence of infrastructure rebuild testing (Terraform apply to a fresh environment).

## How a tiny AI-first startup satisfies it
- **Annual documented restore test** (calendar it, or let the shadow tool nag when the last log is > 11 months old):
  1. `gcloud sql instances clone` production from a PITR timestamp into `restore-test-YYYYMMDD`.
  2. Run verification queries — row counts on key tables, latest timestamps, a checksum or two — compared against production.
  3. Record start/end time; compare to RTO/RPO in the DR runbook.
  4. Write `compliance/restore-tests/YYYY-MM-DD.md` with procedure, output, verdict, gaps; open Linear tickets for gaps.
  5. Delete the scratch instance.
- **Optionally test infra rebuild**: `terraform plan`/`apply` into a scratch project once a year proves the "recovery infrastructure" leg; even a clean `plan` against an empty state is evidence the code is live.
- **Keep it in the repo**: restore-test logs as markdown in git give immutable timestamps (commit history) — exactly what an auditor samples.
- **Update the plan from findings**: if the test reveals a wrong step in the runbook, the fix commit is itself evidence of a functioning control loop.
- Note: the *execution* of a restore test cannot be fully automated away from human judgment on data integrity, but the shadow tool can automate the verification that a test happened recently and can even orchestrate the mechanical clone-and-count steps.

## Automated shadow checks

> Datastore commands are per-stack: Cloud SQL shown. On Firestore stacks (the blessed `provision/gcp`), the equivalents are `gcloud firestore databases describe` (PITR, delete protection, state) and `gcloud firestore backups list` / `backups schedules list` (schedule present, recent snapshots).
| Check | Source | Method |
|---|---|---|
| Restore test performed within 12 months | GitHub | `gh api repos/<org>/<repo>/contents/compliance/restore-tests/` → newest file's date < 365 days |
| Restore test log has required fields | GitHub | Fetch newest log via `gh api ...contents/...` → grep for date, elapsed time, RTO comparison, verification queries |
| Clone/restore operation actually ran | GCP | `gcloud sql operations list --instance=<inst> --format=json` → operation of type `CLONE`/`RESTORE_VOLUME` near the logged test date |
| Scratch restore instance cleaned up | GCP | `gcloud sql instances list --format=json` → no lingering `restore-test-*` instances older than 7 days |
| DR runbook updated after test gaps | GitHub | `gh api repos/<org>/<repo>/commits?path=docs/runbooks/disaster-recovery.md` → commit after test date if log lists gaps |
| Orchestrated restore drill | GCP | Shadow tool can itself run clone → row-count → teardown and emit the log (semi-automated evidence generation) |
| Data integrity judgment | — | MANUAL — human confirms restored data is complete/correct beyond mechanical counts |
| RTO/RPO target reasonableness | — | MANUAL — auditor judgment |

## Evidence artifacts
- `compliance/restore-tests/YYYY-MM-DD.md` — the test report: procedure, command output, timings, verification results, verdict, gaps. Git history provides the timestamp.
- `gcloud sql operations list` JSON export showing the clone/restore operation matching the test date.
- Terminal transcript or CI job log of the restore drill (if orchestrated via the shadow tool or a script in the repo).
- Linear tickets for gaps found and their closure.
- `docs/runbooks/disaster-recovery.md` diff showing plan updates driven by test findings.
