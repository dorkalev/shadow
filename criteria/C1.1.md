# C1.1 — Identify and protect confidential information

## Criterion (AICPA TSP Section 100, verbatim)
> The entity identifies and maintains confidential information to meet the entity's objectives related to confidentiality.

## What it means
This category is optional — it applies only if the company includes Confidentiality in its SOC 2 scope. Startups usually add it when customer contracts promise confidentiality of customer data (very common for B2B AI products handling customer documents, prompts, or datasets).

"Identifies" means you know what information you hold is confidential — customer data, prompts/completions, API keys, contracts, source code — and you've written that down as a data classification. "Maintains" means that once classified, the information is protected throughout its lifecycle per your commitments: access-restricted, encrypted, retained for a defined period, and not leaking into places outside the classification (logs, analytics tools, LLM training pipelines, personal laptops).

For a tiny AI-first startup the real risks are unglamorous: customer text pasted into third-party LLM APIs without a DPA/no-training terms, prompts and completions landing in plaintext application logs, and production data copied to dev environments. A one-page classification policy plus a table of "where each class of data lives and who can touch it" covers identification; encryption defaults, IAM, and log hygiene cover maintenance.

## Points of focus (2022 revision, summarized)
These are guidance to consider, not requirements:
- **Identifies confidential information** — procedures exist to identify and designate confidential information when it is received or created, and to determine the period over which it must be retained (summary).
- **Protects confidential information from destruction** — designated confidential information is protected against erasure or destruction during its retention period (summary).
- Supporting expectations commonly assessed alongside: classification is reflected in handling requirements (access, encryption, sharing) and confidentiality commitments in customer agreements are traced to those requirements (summary).

## What the auditor will ask for
- Data classification policy defining classes (e.g., Public / Internal / Confidential / Restricted) and handling rules per class.
- Data inventory or data-flow diagram: what confidential data exists, which systems store/process it (DB, buckets, LLM providers, logs), retention period per type.
- Sample customer agreement (MSA/DPA) showing confidentiality commitments, mapped to controls.
- Evidence of access restriction to confidential data stores (IAM policies, DB access list).
- Evidence of encryption at rest and in transit for confidential data stores.
- Subprocessor list (including LLM providers) with agreements covering confidentiality / no-training clauses.
- Retention schedule showing confidential data is preserved for its required period.

## How a tiny AI-first startup satisfies it
- **One-page classification policy** in the repo (`docs/policies/data-classification.md`): 3–4 classes, handling matrix (who can access, encryption, sharing, retention). Reviewed annually via PR.
- **Data inventory as a YAML/markdown file** (`compliance/data-inventory.yaml`): each dataset → classification, system of record, retention, owner. Machine-readable so the shadow tool can diff it against actual cloud resources.
- **Encryption by default**: GCP encrypts at rest automatically; enforce TLS on Cloud SQL (`requireSsl`) and HTTPS-only on services — cheap, verifiable wins.
- **IAM as classification enforcement**: confidential stores get least-privilege bindings; no `allUsers`/`allAuthenticatedUsers` on buckets; per-service accounts instead of shared keys.
- **LLM provider hygiene**: use API tiers with no-training/zero-retention commitments (e.g., commercial API terms), list providers as subprocessors, and keep the signed terms/DPAs in the vendor folder.
- **Log hygiene**: policy statement + code practice that prompts/completions and secrets are not written to plaintext logs, or are redacted; spot-checkable.
- **Protect from premature destruction**: bucket versioning/soft-delete and DB backups (A1.2) double as the "protected from destruction during retention" evidence.

## Automated shadow checks

> Datastore commands are per-stack: Cloud SQL shown. On Firestore stacks (the blessed `provision/gcp`), the equivalents are `gcloud firestore databases describe` (PITR, delete protection, state) and `gcloud firestore backups list` / `backups schedules list` (schedule present, recent snapshots).
| Check | Source | Method |
|---|---|---|
| Classification policy exists, reviewed < 12 months | GitHub | `gh api repos/<org>/<repo>/contents/docs/policies/data-classification.md` + `gh api .../commits?path=...` → last commit date |
| Data inventory exists and parses | GitHub | `gh api .../contents/compliance/data-inventory.yaml` → fetch, validate schema (class, system, retention, owner per entry) |
| Inventory matches real resources | GCP | `gcloud sql instances list` / `gcloud storage buckets list --format=json` → every prod store appears in inventory; flag unlisted resources |
| No public buckets | GCP | `gcloud storage buckets get-iam-policy gs://<bucket> --format=json` → no `allUsers` / `allAuthenticatedUsers` bindings |
| TLS enforced on DB | GCP | `gcloud sql instances describe <inst> --format="value(settings.ipConfiguration.sslMode)"` → `ENCRYPTED_ONLY` / require SSL |
| Bucket versioning/soft delete (destruction protection) | GCP | `gcloud storage buckets describe gs://<bucket> --format=json` → versioning or softDeletePolicy enabled |
| Subprocessor/vendor list current | GitHub | `gh api .../contents/compliance/subprocessors.md` → exists; LLM providers present; last review date < 12 months |
| Secrets not in repo | GitHub | `gh api repos/<org>/<repo>/secret-scanning/alerts` → secret scanning enabled, no open alerts |
| Logs free of confidential data | — | MANUAL — sample application logs for prompts/PII/secrets |
| Contract commitments map to controls | — | MANUAL — auditor traces MSA/DPA language to the handling matrix |

## Evidence artifacts
- `docs/policies/data-classification.md` — classes and handling matrix, with PR approval history as review evidence.
- `compliance/data-inventory.yaml` — machine-readable inventory of confidential data, systems, retention, owners.
- `compliance/subprocessors.md` — vendor/LLM provider list plus stored DPAs/no-training terms (Drive folder link acceptable for signed PDFs).
- IAM policy JSON exports for confidential stores (buckets, Cloud SQL, project) at evidence-collection time.
- `gcloud` exports proving TLS enforcement and versioning/soft-delete settings.
- Sample redacted customer MSA/DPA showing confidentiality commitments.
