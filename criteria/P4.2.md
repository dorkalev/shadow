# P4.2 — Retention Consistent with Objectives

## Criterion (AICPA TSP Section 100, verbatim)
> The entity retains personal information consistent with the entity's objectives related to privacy.

## What it means
The Privacy category is optional — it applies only if the company includes Privacy in its SOC 2 scope (most tiny startups don't; they cover privacy via GDPR/CCPA programs instead).

Keep personal information only as long as you said you would, and only as long as you need it. That requires two things: a retention schedule (per data category: how long, and why — legal requirement, business need) and mechanisms that actually enforce it. "We keep everything forever because deleting is hard" fails this criterion; so does a beautiful retention policy with no cron job behind it.

For a tiny AI startup, the usual hot spots are: LLM request/response logs (often the most sensitive store you have — set short TTLs), analytics events, support email threads, backups (retention schedules must acknowledge backup cycles), and churned-customer data (define a post-termination deletion window, commonly 30–90 days, and honor it).

## Points of focus (2022 revision, summarized)
These are summaries of the AICPA points of focus, not verbatim:
- Retention periods for personal information are defined, documented, and consistent with the privacy notice, commitments, and legal requirements.
- Personal information is retained only as long as necessary to fulfill the stated purposes.
- Retention practices are applied to all copies, including logs and backups, per the schedule.
- Retention schedules are reviewed periodically and updated for new data types or changed requirements.

## What the auditor will ask for
- The documented retention schedule (per data category, with periods and rationale).
- Evidence of enforcement: TTL/lifecycle configurations, scheduled deletion job code and its run logs.
- Sample verification: records older than the retention period do not exist (query output).
- Backup retention configuration and how deleted data ages out of backups.
- Churned-customer offboarding evidence: a departed customer's data deleted within the committed window.
- Review evidence: the retention schedule was reviewed during the period (ticket/PR).

## How a tiny AI-first startup satisfies it
- Write `compliance/retention-schedule.md`: one table — category, store, period, enforcement mechanism. Keep it to a page (users: life of account + 30 days; LLM logs: 30 days; analytics: 14 months; backups: 35 days; support email: 24 months).
- Enforce with platform primitives, not custom code where possible: GCS/S3 lifecycle rules, log sink retention (Cloud Logging retention days), Postgres cron job (`pg_cron` or a scheduled Cloud Run job) deleting expired rows, analytics tool retention setting.
- Backups: rely on managed rotation (e.g., Cloud SQL automated backups, 7–35 days) so deleted data ages out automatically; document that window in the schedule.
- Churn: a runbook + Linear ticket template "Offboard customer X" with a deletion checklist; close with query output proving zero rows.
- Annual review as a recurring Linear ticket, closed with a PR (even a no-op date bump).

## Automated shadow checks

> Datastore commands are per-stack: Cloud SQL shown. On Firestore stacks (the blessed `provision/gcp`), the equivalents are `gcloud firestore databases describe` (PITR, delete protection, state) and `gcloud firestore backups list` / `backups schedules list` (schedule present, recent snapshots).
| Check | Source | Method |
|---|---|---|
| Retention schedule file exists, parses, and reviewed within 12 months | GitHub | File existence; last-commit date; presence of recurring review ticket in Linear |
| Bucket lifecycle rules match schedule | GCP/AWS | `gcloud storage buckets describe` / `aws s3api get-bucket-lifecycle-configuration`; compare TTL days to schedule |
| Log retention settings match schedule | GCP/AWS | `gcloud logging buckets describe` retentionDays / CloudWatch `retentionInDays` |
| Scheduled deletion job exists and ran recently | GCP/AWS/GitHub | `gcloud scheduler jobs list` / cron workflow in repo; last successful run within expected interval |
| Backup retention window configured as documented | GCP/AWS | `gcloud sql instances describe` backup settings / `aws rds describe-db-instances` |
| No rows older than retention period in PI tables | Production DB | Read-only count query via approved reporting connection (`SELECT count(*) WHERE created_at < now() - interval`) |
| Churned-customer deletion completed within window | Linear + DB | Query offboarding tickets; MANUAL confirmation of query-output attachment |

## Evidence artifacts
- `compliance/retention-schedule.md` with git history and annual-review commits.
- Lifecycle/retention config exports: bucket lifecycle JSON, logging retention settings, backup config.
- Deletion job source code and execution logs (scheduler run history) for the period.
- Query outputs showing zero over-retained rows, stored in `compliance/evidence/retention-check-<date>.txt`.
- Closed Linear offboarding tickets with deletion checklists and proof attachments.
- Analytics tool retention setting screenshot/export.
